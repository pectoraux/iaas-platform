# ACR-003 — Promote the Extension Stack Boundary

- ACR-ID: `ACR-003`
- Status: `UNDER_REVIEW`
- Requested by: Chief Architect (via WORK-014)
- Affected Architecture Version: `IAAS-DOM-ARCH-3` (FROZEN)
- New Architecture Version: `IAAS-DOM-ARCH-4` (candidate — pending Architect approval)
- Affected Requirements: `DOM-P04` (Extension + ExtensionRegistry + ExtensionRuntime)
- Affected Work Items: `WORK-014` (architecture freeze)

## Current Rule

`IAAS-DOM-ARCH-3` §4 defers Extension sandbox technology, marketplace, SDK, and
cryptographic certification as OPEN/RESEARCH. `DOM-P04` in V1 requirements is
FUTURE. No Extension contract exists in the frozen architecture.

## Problem / Evidence

The Transform Stack (V3) established a proven pattern: freeze the contract
before implementation. The Extension Stack needs the same treatment: a frozen
contract for `Extension`, `ExtensionRegistry`, and `ExtensionRuntime` that
defines identity, capabilities, lifecycle, security/isolation, and anti-
dependencies — without committing to a sandbox technology or implementing
extensions.

The constitution §10 defines the Extension boundary at a high level. This ACR
operationalizes it into a frozen domain architecture version.

## Proposed Change

Promote `Extension`, `ExtensionRegistry`, and `ExtensionRuntime` from FUTURE
to FROZEN-CONTRACT in a new `IAAS-DOM-ARCH-4`. The contract MUST:

1. Define `Extension` as an abstract pluggable operation contract (routing
   strategy, scheduling, mobility prediction, cache strategy, deduplication,
   protocol algorithms, security behavior, transforms — per constitution §10).
2. Define `ExtensionRegistry` as discovery/catalog/version-compatibility/
   certification/revocation/lifecycle metadata — does NOT execute.
3. Define `ExtensionRuntime` as execution/isolation engine — resolves via
   Registry, enforces capability/resource limits, emits provenance.
4. Define tenant isolation, capability declaration, dependency boundaries,
   resource limits, security/isolation obligations without selecting a sandbox
   technology (WASM/container/native remains OPEN/RESEARCH).
5. Define the Extension↔Transform relationship: Extensions MAY use Transforms
   but the two stacks remain distinct; neither becomes the other.
6. Define anti-dependencies: Extension Stack MUST NOT import vertical services,
   EconomicPipeline, Route/Transport, RuntimeRegistry, or kernel code.
7. Preserve `DOM-P05..P08` (Marketplace, SDK, Fragmentation, sandbox tech) as
   FUTURE/OPEN/RESEARCH.

`Extension` MUST NOT become:
- a kernel primitive;
- a marketplace entry;
- a replacement for TransformRegistry/TransformRuntime;
- a vertical-specific plugin.

## Architectural Questions

1. **Sandbox technology**: remains OPEN/RESEARCH. The contract defines
   isolation *obligations* (resource limits, capability scoping, provenance)
   without selecting WASM/container/native. Implementation selects technology
   in a future Work Item.
2. **Extension↔Transform relationship**: Extensions MAY invoke Transforms via
   the TransformRuntime contract. Extensions do NOT own TransformRegistry or
   TransformRecord. The relationship is one-way: Extension → TransformRuntime
   (resolve + execute), not vice versa.
3. **Security/certification**: the contract defines *metadata* fields for
   publisher identity, signature status, and certification status — without
   freezing a cryptographic mechanism. Concrete signature infrastructure is
   future.
4. **Marketplace**: explicitly NOT part of this ACR. Discovery/publishing/
   licensing/commercial remains `DOM-P05` FUTURE.

## Alternatives Considered

### Keep Extension as FUTURE
Rejected: the Transform Stack proved that freezing the contract before
implementation prevents drift and enables regression testing.

### Merge Extension into Transform Stack
Rejected: Extensions are pluggable operations (routing, scheduling, caching,
deduplication); Transforms are payload operations. Conflating them violates
the constitution §9/§10 boundary.

### Select sandbox technology now
Rejected: WASM/container/native selection is an implementation decision that
does not affect the architectural contract. Premature commitment would limit
future flexibility.

## Compatibility / Migration Impact

V3 remains immutable. V4 is a new version that preserves V3 except for the
Extension Stack boundary addition. No production code changes. No Prisma
schema changes. No Transform Stack modifications.

## Verification Impact

Add static architecture checks proving the Extension Stack anti-dependencies.
Add regression tests proving V3 immutability and DOM-P04 non-promotion until
ACR-003 is approved.
