V1-V5 remain immutable; no V6 semantic is altered by the approval or the freeze.

## Decision Intent

This ACR proposes `IAAS-DOM-ARCH-6` as the architecture-completion baseline for the IAAS platform.

V5 remains immutable. No historical architecture document is rewritten. V6 is a new candidate architecture that consolidates the universal contracts, ownership rules, dependency directions, lifecycle semantics, trust boundary, packaging boundary, operational boundary, network launch model, and remaining implementation DAG required to make implementation primarily mechanical rather than exploratory.

No V6 implementation Work Item is authorized until this ACR and the V6 architecture package are independently reviewed and approved.

## 1. Problem / Current Limitations

The repository has strong V1-V5 foundations, including identity/resource separation, immutable network versions, deterministic allocation/execution, runtime isolation, a generic economic pipeline, a service-layer Node, the Data Plane, the Transform Stack, the Extension Stack, and the V5 WASI sandbox contract. The repository also contains production slices through the WORK-021 sandbox host and a released WORK-022 lifecycle-completion Work Order.

However, the canonical specification still contains deferred or inconsistent architectural areas:

1. The top-level `spec/architecture.md` and `spec/architecture-lock.md` lag the V5 canonical domain architecture.
2. V1-derived documentation still contains statements that later versions have superseded, without a single V6 completion baseline.
3. Network definition is implemented, but NetworkInstance, composition, launch/provisioning semantics, and lifecycle ownership are not yet a canonical cross-cutting model.
4. Allocation has deterministic scheduling and capacity reservation/commitment, but temporal/availability semantics and strategy abstraction are not captured as one generic contract.
5. Fragmentation/Reassembly is explicitly deferred despite the Data Plane being intended for DTN/local-first/transit use cases.
6. Trust/signature semantics, package integrity, package compatibility, publisher identity, and artifact verification are not yet a unified architecture.
7. Extension distribution and marketplace boundaries are described only conceptually; technical catalog/lifecycle authority, distribution, commerce, and execution remain insufficiently separated in one V6 contract.
8. Economics lacks a canonical generic metering/usage/attribution/pricing boundary between verified operational facts and ledger/settlement.
9. Operational infrastructure lifecycle and observability/evidence semantics are distributed across existing services rather than being named as one generic architectural layer.
10. SDK and federation are not clearly classified as consumers/cross-domain boundaries versus kernel primitives.
11. Reference-network documents provide coverage evidence but are not tied to a formal V6 conformance matrix.

## 2. Repository Archaeology / Truth Classification

### OBSERVED

- V5 is explicitly marked FROZEN and identifies itself as the successor to V4 through ACR-004.
- The latest main commit is the WORK-022 governance release; WORK-021 is verified and WORK-022 is READY on main.
- Production code contains `Node`, the Data Plane, Transform Stack, Extension Stack, `SandboxHost`, and active sandbox execution/revocation infrastructure.
- The schema is PostgreSQL-only and already persists network, resource, node, data-plane, transform, extension, and economic state.
- `spec/architecture.md` and `spec/architecture-lock.md` still identify V4 as canonical, creating planning-layer drift relative to V5.

### CONFIRMED

- Frozen runtime separation: InfrastructureRuntime, ProtocolRuntime, HybridRuntime, with HybridRuntime as the only bridge.
- Frozen operations/economics separation and Data Plane/economics independence.
- Frozen identity distinctions: Asset, Device, Node, ParticipantIdentity, ResourceIdentity remain separate.
- Frozen ExtensionRegistry/ExtensionRuntime/ExtensionProvenance responsibility boundaries.
- Frozen V5 sandbox capability and deny-by-default contract.

### INFERRED

- The remaining universal gaps can be completed without expanding the kernel into a vertical implementation stack.
- NetworkInstance, composition bindings, fragment/reassembly state, trust envelopes, generic package metadata, economic attribution, and operational lifecycle can be modeled as service/domain boundaries rather than kernel-owned vertical primitives.

### PROPOSED

The V6 additions described in this ACR and the accompanying candidate documents are proposed architecture until ACR-005 is approved and V6 is frozen.

## 4. Universal-Primitive Test

A V6 primitive is promoted only if at least three materially different network classes can reuse it without adding a vertical-specific field, special case, or kernel import.

V6 therefore promotes universal abstractions for network instances, composition, allocation coordination, fragmentation/reassembly, trust envelopes, packages, economic attribution, operational lifecycle, and observability/evidence contracts.

V6 does not promote vertical capabilities such as `energy_discharge`, `gpu_compute`, `transit_bandwidth`, or manufacturing-specific quality rules into the kernel. Those remain network-defined capabilities and policies.

## 5. Authority Model

Exactly one owner is assigned to each responsibility:

- Identity authority → Identity/Participant services.
- Resource truth → Resource/Capacity subsystem.
- Network definition/version authority → Network service.
- Network instance/lifecycle authority → Network Lifecycle subsystem.
- Composition contract authority → Network Composition subsystem.
- Allocation decision authority → Allocation/Scheduler subsystem.
- Reservation/commitment authority → Capacity subsystem.
- Execution authority → Execution subsystem.
- Runtime resolution authority → RuntimeRegistry.
- Node lifecycle authority → Node service.
- Data transport authority → Data Plane / Route / Transport services.
- Transform catalog authority → TransformRegistry.
- Transform execution authority → TransformRuntime.
- Extension catalog/lifecycle authority → ExtensionRegistry.
- Extension execution/isolation authority → ExtensionRuntime + Sandbox boundary.
- Package verification authority → Trust/Package Verification subsystem.
- Operational lifecycle authority → Operations subsystem.
- Verification authority → Verification subsystem.
- Economic attribution authority → Economics Attribution subsystem.
- Ledger authority → Ledger subsystem.
- Settlement instruction authority → Settlement subsystem.
- Distribution/commerce authority → Marketplace boundary.
- Observability authority → Observability subsystem; observations do not become verified truth automatically.

No component may own another component's authoritative state merely because it consumes it.

## 6. Dependency Direction

The V6 dependency direction remains a DAG:

```text
Identity / Resource
        ↓
Network Definition / Template
        ↓
Network Composition / Resolution
        ↓
Allocation / Reservation / Commitment
        ↓
Execution / Lease
        ↓
Runtime / Node
        ├──────────────→ Data Plane
        └──────────────→ Verification
                               ↓
                        Economic Attribution
                               ↓
                        Contribution / Reward
                               ↓
                         Ledger / Settlement

Cross-cutting contracts:
Trust / Package Verification
Observability / Evidence
Operations
SDK
Marketplace
Federation (open)
```

The Data Plane and generic Economic Pipeline remain parallel substrates. Neither acquires a dependency on the other.

The kernel remains contract/enforcement oriented. It does not own NetworkInstance, Marketplace, Package, Economics, Observability, or vertical network behavior.

## 7. Trust and Package Boundary

V6 freezes semantics, not concrete algorithms.

```text
Identity
  ↓
Credential / Key Binding
  ↓
Signature Envelope
  ↓
Trust Policy Evaluation
  ↓
Trust Decision / Verification
```

For installable artifacts:

```text
PackageManifest + Artifacts + Dependencies + Compatibility
                ↓
          Integrity verification
                ↓
          Signature verification
                ↓
       Publisher / trust evaluation
                ↓
      Registry admission / installation
```

A package does not execute because it is verified. Execution remains owned by the relevant runtime.

## 8. Network-as-Code

A NetworkDefinition is declarative. A NetworkManifest is its serialized external/package representation and is not an independent source of truth.

The lifecycle is:

```text
Definition
  → Validation
  → Dependency Resolution
  → Capability Resolution
  → Resource Discovery
  → Allocation
  → Reservation
  → Commitment
  → Provisioning
  → Runtime Activation
  → Verification
  → DEPLOYED
```

The lifecycle of a NetworkInstance is distinct from the control-plane request lifecycle and from the lifecycle of individual resources.

## 9. Network Composition

Composition is explicit and reference-based:

```text
NetworkComposition
  ├─ NetworkDependency
  ├─ CapabilityBinding
  ├─ ResourceBinding
  ├─ PolicyBinding
  ├─ NetworkExport
  └─ NetworkImport
```

Composition contracts expose only stable exported capabilities and resource/policy references. Internal implementation state is never a composition API.

Composition must not bypass tenant authorization, resource ownership, runtime resolution, or network-version immutability.

## 10. Allocation / Temporal Coordination

Allocation remains a policy-driven service boundary. Stable strategy types are capabilities of the allocation subsystem, not kernel branches.

The architecture recognizes:

- exclusive/shared/pooled allocation;
- scheduled/opportunistic allocation;
- fair/priority allocation;
- market/auction strategies as optional policies.

Temporal coordination uses reservation/availability windows and demand constraints. Forecasts are advisory inputs. Allocation decisions remain authoritative only when persisted through the allocation/reservation boundary.

## 11. Data Plane Completion

The Data Plane remains:

```text
Bundle → Route → TransportExecution → TransportAttempt → DeliveryConfirmation
```

V6 adds:

```text
Bundle
  └→ Fragment[]
       └→ ReassemblyState
```

Fragments have immutable identity, sequence/index, total-count when known, integrity, expiry, and tenant scope. Reassembly is idempotent, duplicate-safe, expiration-aware, and must never create cross-tenant assembly state.

## 12. Economics Completion

The operational/economic boundary is:

```text
Operational Fact
   ↓
Verification / Attestation
   ↓
UsageMeasurement
   ↓
EconomicAttribution
   ↓
Contribution / Reward
   ↓
LedgerPosting
   ↓
Settlement instruction
```

PricingPolicy and MeteringRule are policy/configuration contracts. They do not alter operational truth. Economic outcomes cannot mutate Event, VerificationResult, Attestation, Execution, Route, Transport, or other operational source records.

## 13. Operations

Operational resource lifecycle is distinct from workflow/control-plane lifecycle:

```text
PROVISION → VALIDATE → ACTIVATE → PAUSE → RESUME → SCALE → DRAIN
→ UPGRADE → ROLLBACK → TERMINATE → ARCHIVE
```

The exact subset supported by a resource type is declared by its lifecycle capability. Operations owns lifecycle transitions; domain services remain responsible for domain-specific policy.

## 14. Observability and Evidence

These are distinct:

- Telemetry: raw measurements/signals.
- Metric: aggregated numeric observation.
- Log: structured diagnostic record.
- Trace: causal execution/span record.
- Event: immutable domain occurrence used as an evidence record when its semantics require.
- Evidence: an observation package intentionally submitted to verification.
- Verification: policy-driven determination over evidence.
- Attestation: durable verified claim.

Raw telemetry/logs/traces never become verified truth merely by existing.

## 15. Marketplace / Distribution

Marketplace is a distribution/commerce boundary, not a runtime or technical registry replacement.

```text
Package → Registry / Trust Verification → optional Marketplace Publication
                                             ↓
                                        Consumer discovery
                                             ↓
                                      installation request
                                             ↓
                                   technical registry admission
                                             ↓
                                           Runtime
```

Marketplace may manage listings, commercial terms, licenses, and discovery. It must not execute extensions or become the technical authority for runtime lifecycle.

V6 does not freeze a single pricing, commission, licensing, payment provider, or commercial model.

## 16. SDK

The SDK exposes canonical contracts only:

```text
SDK → IAAS API / canonical service contracts
```

It does not introduce private semantics, alternate state machines, or hidden persistence. Local agents and remote fleet clients may use the same canonical contract family.

## 17. Federation

Federation is intentionally OPEN / RESEARCH in V6.

The architecture records the future boundary:

```text
Local IAAS
   ↕
Federation Gateway / Trust Boundary
   ↕
Remote IAAS
```

Candidate future concepts include remote identity, remote network, remote capability/resource, trust anchor, cross-domain execution, and cross-domain settlement. These are NOT frozen because the security, jurisdiction, failure, and economic semantics require additional research and a separate ACR.

## 18. Reference Network Conformance

Reference networks are validation cases, not platform primitives. V6 requires proof that the same generic model can express at least:

- compute;
- storage;
- wireless/bandwidth;
- DTN/transit/local-first;
- manufacturing/industrial;
- mobility;
- energy/VPP;
- protocol/blockchain-style networks;
- community-finance style networks.

No reference network may require a generic-kernel modification or a vertical-specific generic service import.

## 19. Explicit Non-Inclusions

The following remain implementation/configuration choices or separate product concerns:

- specific cloud provider;
- specific payment provider;
- specific marketplace business model;
- specific blockchain;
- specific optimization library;
- specific WASI runtime/version;
- specific cryptographic algorithm;
- specific package archive format;
- specific database beyond the already-frozen PostgreSQL persistence contract.

The following are explicitly rejected as universal primitives:

- NodeAgent as a mandatory domain abstraction;
- a catch-all UniversalNetwork object;
- a second generic ledger;
- a second transform registry inside marketplace/distribution;
- vertical-specific kernel services;
- economics-owned operational state;
- marketplace-owned runtime lifecycle;
- SDK-owned alternate semantics.

## 20. V5 Compatibility / Migration

- V1-V5 documents remain immutable historical records.
- V5 remains the current canonical architecture until V6 is frozen.
- Existing V5 sandbox contract remains unchanged.
- Existing ExtensionRegistry/Runtime/Provenance interfaces remain valid.
- Existing Data Plane objects remain valid; fragmentation/reassembly adds missing capability without changing existing bundle/route/transport semantics.
- Existing economic objects remain valid; V6 adds generic attribution/metering boundaries rather than replacing the ledger.
- Existing NetworkDefinition/Version remain the source of versioned network intent; NetworkInstance is a new deployment identity, not a replacement for NetworkDefinition.
