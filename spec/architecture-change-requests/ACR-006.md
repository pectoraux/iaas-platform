## 1. Problem / Evidence — exact reproduction of the contradiction

The frozen V6 package contains an internal requirements-to-Work-Item contradiction. Exact quotes from the frozen documents on `main` @ `39ce662`:

1. `spec/domain-requirements-v6.md` line 32:

   ```text
   ## NET-003 — Network Lifecycle Authority
   ```

2. `spec/domain-requirements-v6.md` line 39:

   ```text
   ## NET-004 — Deterministic Network Launch
   ```

3. `spec/work-items-v6.md` line 58 (WORK-026 — Network-as-Code Validation and Launch Compiler):

   ```text
   Requirements: `NET-003`, `NET-004`
   ```

4. `spec/work-items-v6.md` line 44 (WORK-025 — NetworkInstance and Network Lifecycle):

   ```text
   Requirements: `NET-001`, `NET-002`
   ```

5. `spec/work-items-v6.md` line 240 (WORK-040 — Universal Network Launch Proof):

   ```text
   Requirements: `NET-004`, `REF-001`, `CONF-001`
   ```

6. `spec/work-orders/WORK-026.md` line 12 mirrors the ledger: `Acceptance: NET-003-AC01..04; NET-004-AC01..04.`

Why this is a live blocker and not a labeling nuance:

- **NET-003** (Network Lifecycle Authority) requires provision/validate/activate/pause/resume/scale/drain/upgrade/rollback/terminate/archive semantics with exactly one authoritative owner, invalid-transition rejection, and workflow-lifecycle separation. That behavior was implemented and verified in **WORK-025** (PR #42: the authoritative NetworkInstance state machine, exhaustive transition matrix, invalid-transition negatives, tenant isolation, audit).
- **NET-004** (Deterministic Network Launch) requires that a valid NetworkDefinition be *launchable* into a NetworkInstance — launch consumes resolved dependencies/capabilities/resources/policies; activation occurs only after provisioning and verification; launch failures cannot create an active instance. Its Verification field names `launch integration tests; failure-atomicity tests; universal-launch proof`. The Work Order released as GitHub Issue #43 explicitly **forbids** WORK-026 from allocation, provisioning, activation, composition, federation, economics, Data Plane, runtime execution, and kernel changes — so WORK-026 cannot satisfy NET-004's frozen acceptance semantics as ledgered. PR #44 (blocked, REQUIRE CHANGES) claimed NET-003/NET-004 because the ledger told it to; that claim is the recorded blocker.
- **NET-002** (Declarative Network-as-Code) requires that the versioned definition "can be **validated and resolved deterministically**" (Verification: `manifest compilation tests; deterministic-resolution tests; reference-network conformance`). That is precisely the scope the Chief Architect issued to WORK-026 (Issue #43: "compile declarative NetworkDefinition into a deterministic launch plan"), and precisely what the blocked PR #44 implements. It is not what WORK-025's ledger line claims.

Because `IAAS-DOM-ARCH-6` is FROZEN, neither the implementer nor the Architect may silently reinterpret these IDs in place (`spec/work-items-v6.md` WORK-041 constraint: "any missing primitive or boundary contradiction routes to `ACR-006+`, never to silent V6 edits"). This ACR is that route.

## 2. Diagnosis — the assignment layer swapped NET-002 and NET-003 and double-assigned NET-004

Each Work Item's **own frozen objective and verification text** identifies which requirement it actually carries. Comparing those texts with the requirement definitions shows the ledger's NET-002/NET-003 assignments are transposed between WORK-025 and WORK-026, and NET-004 is assigned both to its mechanism-agnostic planning item and to its proof item:

| Frozen Work Item text | Matches requirement | Ledger says | Verdict |
|---|---|---|---|
| WORK-025 objective: "implement durable NetworkInstance identity **and lifecycle authority**" | NET-001 (identity) + **NET-003** (Network Lifecycle Authority — title verbatim) | NET-001, NET-002 | ledger wrong on NET-002 |
| WORK-025 Required Verification: "PostgreSQL lifecycle tests, tenant isolation, immutability, audit" | NET-003 Verification ("lifecycle state-machine tests; authority matrix checks; invalid-transition tests") + NET-001 Verification ("persistence and tenant-isolation tests") | (claims NET-002) | same |
| WORK-025 merged implementation (PR #42): authoritative state machine; 12-state frozen §3.4 chart; exhaustive 8×8 matrix; 23 invalid-transition negatives; workflow-distinct ownership; audit | NET-001-AC* + **NET-003-AC*** | (verified against NET-001/NET-002 labels) | behavior is NET-003 |
| WORK-026 objective: "provide deterministic **validation/resolution**/launch planning from declarative NetworkDefinition" | **NET-002** ("can be validated and resolved deterministically") | NET-003, NET-004 | ledger wrong on both |
| WORK-026 Required Verification: "deterministic fixtures, negative ordering tests, static dependency tests" | NET-002 Verification ("deterministic-resolution tests") | (claims NET-003/NET-004) | same |
| Issue #43 Work Order scope: "compile declarative NetworkDefinition into a deterministic launch plan"; prohibitions on allocation/provisioning/activation/runtime execution | **NET-002** semantics exactly; incompatible with NET-004 launch semantics | (mirrors ledger) | order acceptance line wrong |
| WORK-040 objective: "execute end-to-end Network-as-Code launch for representative … networks"; AC: "complete launch lifecycle … proof" | **NET-004** (Verification names `universal-launch proof`) | NET-004 (already listed) | correct — and should be the *sole* owner |

The contradiction is therefore an **assignment-layer defect**: the requirement set itself is internally sound; the ledger (and the work-order acceptance lines mirroring it) transposed NET-002/NET-003 between the two items and double-assigned NET-004.

## 6. WORK-026 boundary preservation (Issue #45 required verification)

Under the corrected mapping, WORK-026 owns exactly `NET-002`. NET-002's obligations are: (a) declarative **versioned definition** — pre-existing NetworkDefinition/NetworkVersion, publication semantics preserved; (b) deterministic **validation** — a pure function over immutable published versions; (c) deterministic **resolution** — dependency/capability/resource resolution, read-only; (d) the launch lifecycle **represented as one lifecycle** — a representational obligation (the canonical pipeline materialized as the deterministic plan artifact), not an execution obligation; (e) the **same model for simple and complex networks** — one compiler path, no vertical branches.

None of (a)–(e) requires allocation, reservation, commitment, provisioning, activation, runtime execution, composition, federation, economics, Data Plane, or kernel changes. The stages beyond resolution are *enumerated* in the plan output for later Work Items — they are never executed by WORK-026. **WORK-026 therefore remains entirely within its current implementation boundary and is not forced to implement launch/activation semantics.** The Issue #43 prohibitions stand untouched.

## 9. Alternatives considered

- **A. Silent reinterpretation in PR #44 (claim NET-002/NET-003 semantics under NET-003/NET-004 labels).** REJECTED — V6 is FROZEN; frozen requirement IDs may not be reinterpreted by the implementer (this is precisely the architect's recorded blocker).
- **B. Rewrite NET-004's text to mean "launch planning" so WORK-026 can own it.** REJECTED — waters down the frozen end-to-end launch semantics (activation-after-provisioning, failure atomicity, universal-launch proof) that the architecture intends and WORK-040 proves; violates "preserving the intended architecture".
- **C. Split NET-004 into a planning requirement (WORK-026) and an execution requirement (new owner).** REJECTED as non-minimal — NET-002 already covers deterministic validation/resolution/planning; a split would duplicate requirement text and disturb CONF-001's dependency list without adding architectural information.
- **D. Add a new dedicated launch-execution Work Item owning NET-004.** REJECTED — changes the frozen DAG structure (new node/edges), which is not a minimum correction; the frozen architecture already distributes launch execution across existing authorities (NET-003 @ WORK-025, ALLOC @ WORK-028, OPS-001 @ WORK-035, OBS-002 @ WORK-036) and already lists NET-004 at WORK-040, whose proof-only scope ("all behavior must use previously implemented contracts; no architectural invention") is exactly NET-004's verification method.
- **E. (CHOSEN) Assignment-layer reallocation** — the transposition fix plus NET-004 sole ownership at WORK-040: the only correction that (i) matches every Work Item's own frozen objective/verification text, (ii) matches the implemented-and-merged reality of WORK-025, (iii) matches the issued WORK-026 scope and its prohibitions, (iv) preserves the requirement set byte-for-byte, (v) leaves the DAG edge set byte-identical, and (vi) requires no new primitives, semantics, or Work Items.
