# ACR-004 — Sandbox Architecture and Isolation Semantics for the Extension Stack

- ACR-ID: `ACR-004`
- Status: `APPROVED`
- Decision date: 2026-08-27 (UTC)
- Affected Architecture Version: `IAAS-DOM-ARCH-4` (FROZEN)
- New Architecture Version: `IAAS-DOM-ARCH-5` (APPROVED FOR FREEZE)
- Governing Architecture: `IAAS-GOV-ARCH-1` (FROZEN)

## Decision

APPROVED. IAAS adopts the WASI Component Model / capability-sandbox contract as the preferred sandbox architecture for untrusted extensions. V5 freezes the architectural contract, not a specific WASI revision or concrete runtime.

V4 remains immutable. This approval authorizes WORK-020 to freeze V5; it does not authorize sandbox implementation.

## Frozen V5 Contract

### Trust Boundary
The WASM component/instance boundary is the trust boundary. Extension code is untrusted; the ExtensionRuntime host is trusted. No ambient authority is permitted. External access requires explicitly granted host capability handles.

### Capability and Resource Authority
ExtensionRuntime remains authoritative under V4 §2.6. Effective authorization is `min(declared, approved)`. The sandbox enforces that ceiling at the operation boundary. Extensions cannot self-authorize.

### Resource Measurement
The following quantities are distinct:

- `executionBudget` / `fuelUnits`: deterministic guest execution budget, never CPU time;
- `cpuTimeNs`: host/runtime CPU measurement when available, never inferred from fuel;
- `wallTimeMs`: host-monotonic elapsed time;
- `peakLinearMemoryBytes`: observed guest linear-memory peak;
- `hostcallBytes`: host/guest transfer accounting.

V5 must expose measurement-source/version semantics so fuel is never silently represented as CPU milliseconds.

### Lifecycle and Termination
```text
registered → installed → activated ⇌ deactivated → revoked
```

Revocation, timeout, and resource exhaustion invoke an architectural termination contract:

```text
terminate sandbox execution context
        ↓
failed provenance
        ↓
terminal outcome / re-throw
```

Concrete runtime APIs remain implementation details.

### Isolation and Failure Containment
Each execution receives isolated sandbox state. Host filesystem, network, memory, devices, and other tenant state are unavailable unless explicitly granted through the capability boundary. Unsandboxed execution is prohibited.

### Fallback
If the preferred sandbox is unavailable, extension execution is denied with `denialReason: 'sandbox_unavailable'`. No silent degradation or implicit container/native fallback is permitted. Alternative sandbox implementations require a separate ACR.

### Provenance
V5 introduces authoritative measured resource/capability semantics for new provenance records. Existing V4 records remain valid historical records and are not migrated.

## Alternatives

WASM/WASI, containers, and native/plugin-process isolation were evaluated across capability enforcement, resource metering, tenant isolation, host I/O control, compromise containment, lifecycle, provenance, portability, operations, and failure semantics.

WASM/WASI provides the strongest overall fit. Container isolation remains a possible future implementation for native-system-access workloads but is not frozen as the primary sandbox. Native/plugin-process isolation is not selected for untrusted extensions.

## Governance Effect

- `IAAS-DOM-ARCH-4` remains FROZEN and immutable.
- `IAAS-DOM-ARCH-5` is authorized for freeze by WORK-020.
- `DOM-P05` is promoted to the V5 sandbox contract when WORK-020 is verified.
- No sandbox implementation is authorized until V5 is frozen and a separate bounded implementation Work Item is released.

## Verification

WORK-019 established the decision and alternatives evidence. WORK-020 verifies the state transition, V4 immutability, V5 completeness, and implementation prohibition before release.
