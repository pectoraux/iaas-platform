# ACR-004 — Sandbox Architecture and Isolation Semantics for the Extension Stack

- ACR-ID: `ACR-004`
- Status: `DRAFT`
- Requested by: Chief Architect (via WORK-019)
- Date: 2026-08-27 (UTC)
- Affected Architecture Version: `IAAS-DOM-ARCH-4` (FROZEN)
- New Architecture Version: `IAAS-DOM-ARCH-5` (CANDIDATE — proposed, NOT frozen by this ACR)
- Affected Requirements: frozen V4 §2.8 Security and Isolation; deferred sandbox area; `DOM-P05` (Sandbox Technology) promotion candidate
- Affected Work Items: `WORK-019`
- Governing Architecture: `IAAS-GOV-ARCH-1` (FROZEN)

## Current Rule

Frozen `IAAS-DOM-ARCH-4` §2.8 states:

> The contract requires capability scoping, resource-limit enforcement, tenant isolation, publisher identity metadata, immutable provenance, and failure containment. Sandbox technology (WASM/container/native) remains OPEN/RESEARCH and is not frozen by V4.

V4 §4 (Deferred Technology / Product Areas) lists sandbox technology alongside Marketplace (`DOM-P05`), SDK (`DOM-P06`), cryptographic mechanism, packaging, pricing/settlement, economic attribution, and Fragmentation/Reassembly (`DOM-P07`/`DOM-P08`) as remaining future/open.

The currently implemented Extension Stack (WORK-016/017/018) enforces capability and resource ceilings at the **declaration/approval** level: `ExtensionRuntime.computeEffectiveCeiling` computes `min(declared, approved)` and denies execution before dispatch if the declared request exceeds the approved authorization. However, because no sandbox is selected, the runtime **cannot observe actual resource usage** or **contain a compromised extension**. The `resourceUsage` and `capabilitiesExercised` fields in `ExtensionProvenancePayload` over-approximate to the effective ceiling rather than measuring real usage. This is safe for trusted extensions but insufficient for untrusted/published extensions.

## Problem / Evidence

The Extension Stack contract (DOM-018..DOM-022) is frozen and implemented, but the **isolation boundary** that makes untrusted extensions safe to execute is not yet defined. Without a sandbox decision:

1. **No compromise containment.** A malicious or buggy extension executing in the host process can access the filesystem, network, environment variables, and other tenants' data in memory. The V4 §2.8 "failure containment" requirement is not satisfiable without an isolation boundary.
2. **No authoritative resource metering.** `ExtensionProvenancePayload.resourceUsage` cannot reflect actual CPU/memory/wall-clock usage; it can only echo the pre-execution ceiling. This makes provenance less useful for auditing, billing, and abuse detection.
3. **No capability enforcement at the syscall boundary.** The runtime denies execution if the declared capabilities exceed the approved set, but it cannot prevent a dispatched extension from performing unauthorized operations (e.g. network access when only `compute.read` was declared).
4. **No portable deployment contract.** Without a frozen sandbox, deployment operators cannot reason about what an extension can and cannot do. This blocks Marketplace (DOM-P05) and SDK (DOM-P06) promotion.
5. **Sandbox is the last OPEN/RESEARCH item blocking a fully-frozen Extension Stack.** All other V4 Extension Stack contracts (Extension, ExtensionRegistry, ExtensionRuntime, ExtensionProvenance) are frozen and implemented.

This ACR resolves the sandbox decision so that a successor architecture version (`IAAS-DOM-ARCH-5`, candidate) can freeze the isolation boundary and authorize future bounded implementation Work Items.

## Evaluation Dimensions

All three candidate sandbox technologies are evaluated against the 10 dimensions required by WORK-019.

### Dimension 1 — Capability Enforcement

The runtime must enforce that an extension cannot perform operations outside its approved capability set. The frozen V4 §2.6 precedence is `min(declared, approved)`; the sandbox must make this enforceable at the actual operation boundary, not just the declaration boundary.

| Technology | Capability Enforcement |
|---|---|
| **WASM/WASI** | Strong. The WASI Component Model provides a capability-based security architecture: a component cannot access any resource (filesystem, network, environment) unless the host explicitly imports a capability handle. The `wasi:io` / `wasi:filesystem` / `wasi:sockets` interface surfaces make every external access an explicit host-granted capability. The host (ExtensionRuntime) can grant exactly the approved capabilities and nothing more. |
| **Container** | Moderate. Linux capabilities (`CAP_*`), seccomp filters, and AppArmor/SELinux profiles can restrict syscalls, but the default container surface is large. Capability enforcement requires a curated seccomp profile per extension — operationally complex and easy to misconfigure. |
| **Native/plugin-process** | Weak. A native plugin in the host process has full host capabilities unless wrapped in seccomp/namespaces (which makes it equivalent to container isolation). A separate process with IPC is better but still requires OS-level restrictions for true capability enforcement. |

### Dimension 2 — Resource Limits and Metering

The runtime must enforce `declaredResourceLimits` and record **authoritative** measurements in provenance. Per AR-019-02, resource metering is defined as **separate distinct quantities**, not a single conflated metric. Fuel (a deterministic execution budget) is NOT inherently CPU time.

| Technology | Resource Limits & Metering |
|---|---|
| **WASM/WASI** | Strong. WASM runtimes provide distinct mechanisms: (a) **fuel/epoch interruption** — a deterministic guest execution budget (instruction-cost); (b) **linear memory limits** — max memory enforced by the runtime; (c) **wall-clock timeouts** — host-side elapsed-time enforcement via epoch deadlines or external supervisors; (d) **CPU time** — host/runtime-measured where available. These are independent mechanisms with distinct failure semantics. This is the most metering-friendly option because each quantity is measured by the appropriate authority. |
| **Container** | Moderate. cgroups v2 enforce CPU/memory/IO limits, but metering requires reading cgroup stats (coarse, async). CPU time is enforceable via `cpu.max`; memory via `memory.max`; wall-clock via an external supervisor. Metering granularity is coarser than WASM fuel. |
| **Native/plugin-process** | Weak-to-moderate. `rlimit`/`setrlimit` enforce per-process limits; `getrusage` reads CPU/memory. But a native plugin in-process cannot be limited without OS primitives, and a separate process requires IPC overhead. |

### Dimension 3 — Tenant Isolation

Cross-tenant access must be structurally impossible. The frozen DOM-022 AC02 prohibits cross-tenant provenance queries; the sandbox must extend this to runtime memory and execution state.

| Technology | Tenant Isolation |
|---|---|
| **WASM/WASI** | Strong. Each WASM instance is a separate linear memory; there is no shared address space. Cross-instance access requires explicit host-mediated shared memory (e.g. `SharedArrayBuffer`), which the runtime can simply not grant. Tenant isolation is structural. |
| **Container** | Strong. Separate containers have separate filesystems, PID namespaces, and network namespaces. Cross-container access requires explicit volume/port mapping. Tenant isolation is structural. |
| **Native/plugin-process** | Moderate. Separate processes have separate address spaces (good), but a plugin in-process shares the host's memory (bad). OS-level multi-tenancy requires process-per-extension, which has IPC overhead. |

### Dimension 4 — Filesystem/Network/Device Access

Extensions must not access the host filesystem, network, or devices except through explicitly granted capabilities.

| Technology | FS/Network/Device Access |
|---|---|
| **WASM/WASI** | Strong. The WASI Component Model requires the host to pass `wasi:filesystem` descriptor handles for every file access and `wasi:sockets` for every network access. Without a granted import, the component cannot perform any I/O. This is the most restrictive default. |
| **Container** | Moderate. Mount namespaces isolate the filesystem, but the default container rootfs is a full Linux distribution. Network namespaces isolate networking, but `--network=host` or port mappings are common escape hatches. Device access is restricted by default but `/dev` can be mounted. Requires careful configuration. |
| **Native/plugin-process** | Weak. A native plugin in-process has full host FS/network/device access. A separate process can be chrooted/namespaced, but this is equivalent to container isolation. |

### Dimension 5 — Process Escape / Compromise Containment

If an extension is compromised (e.g. a memory-safety bug in a native extension, or a logic bug in a WASM module), the blast radius must be contained.

| Technology | Compromise Containment |
|---|---|
| **WASM/WASI** | Strong. WASM is memory-safe by design (linear memory, no arbitrary pointer arithmetic, type safety verified at compile time). A compromised WASM module cannot escape the sandbox without a host-side vulnerability in the runtime (Wasmtime/Wasmer). The blast radius is the module's granted capabilities only. |
| **Container** | Moderate. Container escapes are historically rare but exist (e.g. CVEs in runc, kernel namespaces). A compromised container with elevated capabilities can attempt namespace escape. Requires kernel hardening and capability dropping. |
| **Native/plugin-process** | Weak. A native plugin in-process has full host access on compromise — no containment. A separate process is better but still subject to OS-level escape (shared kernel). |

### Dimension 6 — Lifecycle Integration with ExtensionRegistry/Runtime

The sandbox must integrate with the frozen lifecycle (`registered → installed → activated ⇌ deactivated → revoked`) and the `ExtensionRuntime.executeExtension` flow.

| Technology | Lifecycle Integration |
|---|---|
| **WASM/WASI** | Clean. The runtime compiles a WASM module at `installed` (validate + compile), instantiates at `activated` (grant capabilities), executes at runtime, and drops the instance at `deactivated`/`revoked`. Module compilation can be cached. No process management complexity. |
| **Container** | Complex. Container lifecycle (pull, create, start, stop, remove) maps to extension lifecycle but is heavier. Image management, registry storage, and cleanup are operationally significant. `activated ⇌ deactivated` requires start/stop, not destroy/recreate. |
| **Native/plugin-process** | Moderate. Process spawn/kill maps to lifecycle, but dlopen/loadLibrary (in-process) does not support clean unload. Process-per-extension has IPC overhead. |

### Dimension 7 — Provenance Implications

`ExtensionProvenancePayload.resourceUsage` and `capabilitiesExercised` must reflect **authoritative** measurements, not pre-execution ceilings.

| Technology | Provenance Implications |
|---|---|
| **WASM/WASI** | Best. Fuel consumed, memory used, and capabilities invoked are all exactly measurable by the host. Provenance can record authoritative measurements. The host knows exactly which WASI capabilities were granted and can log which were exercised. |
| **Container** | Moderate. cgroup stats provide CPU/memory measurements but at coarser granularity. Capability logging requires intercepting syscalls (seccomp-bpf with `SECCOMP_RET_TRACE`), which is complex and has performance overhead. |
| **Native/plugin-process** | Weak. `getrusage` provides CPU/memory but not capability-level auditing. Native in-process plugins cannot be capability-audited without binary instrumentation. |

### Dimension 8 — Portability and Deployment Model

The sandbox must be portable across deployment environments (Vercel, self-hosted, edge).

| Technology | Portability |
|---|---|
| **WASM/WASI** | Best. WASM is a portable bytecode — compile once, run anywhere with a WASI runtime. Vercel (Node.js) can run Wasmtime via native addons or Wasmer-JS. Self-hosted can run any WASM runtime. Edge runtimes (Cloudflare Workers, Deno Deploy) natively support WASM. |
| **Container** | Moderate. Requires a container runtime (Docker/containerd) at the host. Vercel does not support arbitrary container execution in serverless functions. Self-hosted is fine. Edge is not supported. |
| **Native/plugin-process** | Poor. Native plugins are architecture/OS-specific (x86_64 Linux .so vs arm64 macOS .dylib vs Windows .dll). Not portable across deployment environments without per-platform compilation and distribution. |

### Dimension 9 — Operational Complexity

| Technology | Operational Complexity |
|---|---|
| **WASM/WASI** | Low. Single binary dependency (Wasmtime/Wasmer). No image registry, no container daemon, no namespace management. Module compilation is fast and cacheable. |
| **Container** | High. Requires container runtime, image registry, image build pipeline, storage management, cleanup, security scanning. Operationally significant. |
| **Native/plugin-process** | High. Requires per-platform compilation, distribution, versioning, ABI compatibility management, crash recovery. |

### Dimension 10 — Failure and Termination Semantics

What happens when an extension fails, exceeds a resource limit, or is revoked mid-execution?

| Technology | Failure/Termination |
|---|---|
| **WASM/WASI** | Clean. Fuel exhaustion raises a trap (catchable by host). Timeout raises a trap. Memory limit raises a trap. The host catches the trap, emits failed provenance, and re-throws. Revocation = drop the instance (instant, no cleanup needed). |
| **Container** | Moderate. OOM-killed by cgroups (SIGKILL — not catchable). CPU throttled (not killed). Timeout requires external supervisor to `docker kill`. Revocation = stop + remove container (slow, requires cleanup). |
| **Native/plugin-process** | Poor. A crashed native plugin in-process crashes the host. A separate process can be SIGKILLed but cleanup is OS-dependent. Revocation = kill process (moderate). |

## Proposed Change

**Recommendation: the WASI Component Model / capability-sandbox contract as the preferred sandbox architecture, with container isolation as a documented fallback for extensions that require native system access (e.g. GPU compute, hardware peripherals).**

Per AR-019-01, this ACR freezes the **architectural contract** (the WASI Component Model capability-sandbox semantics), NOT a specific WASI version or runtime. The concrete WASI revision (0.2.x / 0.3.x / future) and concrete runtime (Wasmtime, Wasmer, WasmEdge, etc.) are **implementation choices** governed separately by compatibility and security policy. This preserves upgrade compatibility so a future WASI revision does not require another architecture redesign.

**Compatibility baseline (minimum supported WASI/component ABI):**
- The Component Model interface type system (`wasi:io` and successor interfaces).
- Capability-based resource access (no ambient authority; every external access requires an explicitly imported handle).
- At minimum, the `wasi:filesystem` and `wasi:sockets` interface surfaces (or their successors) for filesystem/network capability scoping.
- A future WASI revision (e.g. 0.3.x, 1.0) is acceptable as long as it preserves the capability-sandbox contract: no ambient authority, explicit host-granted handles, and deterministic resource-limit enforcement.

### Trust Boundary (W019-AC02)

The sandbox trust boundary is the **WASM component/instance boundary**. Code inside the WASM component is untrusted; code outside (the ExtensionRuntime host) is trusted. The host grants capabilities to the component via imported WASI handles; the component cannot perform any operation without an explicitly granted handle.

The `ExtensionRuntime` remains the capability/resource authority (V4 §2.6 precedence unchanged): it computes `min(declared, approved)` and grants exactly that effective ceiling to the sandbox. The sandbox enforces the ceiling at the operation boundary.

### Capability/Resource Authority (W019-AC03)

- **Authority:** `ExtensionRuntime` (unchanged from V4). The runtime computes the effective ceiling and grants it to the sandbox.
- **Precedence:** `min(declared, approved)` (V4 §2.6, unchanged).
- **Enforcement:** the sandbox enforces **distinct** resource limits via independent mechanisms (see §Provenance and Authoritative Resource Measurement below): deterministic execution budget (fuel/epoch), linear memory limits, wall-clock timeouts, and host-measured CPU time where available. Capabilities are enforced by the host granting only the approved WASI component imports.

### Lifecycle/Revocation/Termination (W019-AC04)

- `registered → installed`: validate + compile the WASM module (no instantiation).
- `installed → activated`: instantiate the module with the effective capability/resource ceiling.
- `activated ⇌ deactivated`: keep the instance alive (activated) or drop it (deactivated). Re-activation re-instantiates.
- `revoked` (terminal): drop the instance and evict the compiled module from cache. Future execution is denied by `ExtensionRuntime` (already implemented in V4).
- **In-flight execution on revocation:** the host invokes the **architectural termination contract** (see below). The extension's sandbox execution context is terminated; the extension observes this as a trap/interruption. `ExtensionRuntime` catches the interruption, emits failed provenance with `denialReason: 'revoked_mid_execution'`, and re-throws a `ValidationError` to the caller.
- **In-flight execution on resource exhaustion:** the sandbox raises an interruption/trap for the exhausted resource (execution budget depleted, memory limit exceeded, wall-clock deadline exceeded). `ExtensionRuntime` catches it, emits failed provenance with `failureMetadata.errorType` identifying the exhausted resource, and re-throws.

**Architectural Termination Contract (AR-019 clarification):**

Revocation and termination are defined as an **architectural abstraction**, not a dependency on a particular runtime API:

```text
revoke / resource-exhaustion / timeout
        ↓
terminate sandbox execution context
        ↓
failed provenance emission
        ↓
re-throw / terminal outcome
```

The concrete runtime mechanism for "terminate sandbox execution context" is an **implementation choice**. For example, in Wasmtime the lifetime model is Store-owned: instances are owned by a `Store`, and dropping (or draining) the `Store` deallocates its WebAssembly objects. In other runtimes the mechanism may differ (e.g. explicit instance deallocation, actor termination, process kill). The architecture freezes only the **contract** — that revocation/termination MUST (a) halt the extension's execution, (b) be catchable by the host as an interruption, (c) allow the host to emit failed provenance, and (d) not leave the sandbox in a partially-executed state. The specific API call is defined by the implementation contract, not this ACR.

### Provenance and Authoritative Resource Measurement (W019-AC05)

`ExtensionProvenancePayload.resourceUsage` is upgraded from a pre-execution ceiling echo to an **authoritative post-execution measurement**. Per AR-019-02, resource metering is defined as **separate distinct quantities** — fuel is a deterministic execution budget, NOT inherently CPU time. Memory limiting and wall-clock enforcement are distinct mechanisms.

**Authoritative measurement model (V5 candidate):**

```text
executionBudget / fuelUnits   = deterministic guest execution budget consumed
                                 (instruction-cost; measured by the sandbox runtime)
cpuTimeNs                      = host/runtime-measured CPU time (if available;
                                 otherwise absent — NOT derived from fuel)
wallTimeMs                     = host-measured elapsed wall-clock time
peakLinearMemoryBytes          = runtime-observed guest linear memory peak
hostcallBytes                  = host/guest transfer accounting (bytes copied
                                 across the sandbox boundary)
```

**Measurement authority and units:**
- `executionBudget` (`fuelUnits`, unitless integer): authoritative source = the sandbox runtime's fuel/epoch accounting. This is a **deterministic execution budget**, not CPU time. It is the primary mechanism for enforcing `cpuMs`-equivalent limits: the host converts the approved `cpuMs` ceiling to a fuel budget via a calibrated multiplier, and fuel exhaustion terminates execution.
- `cpuTimeNs` (nanoseconds): authoritative source = the host runtime's CPU-time accounting (e.g. `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` or runtime-native CPU profiling), **if available**. If the runtime does not expose CPU time, this field is absent. It is NOT derived from fuel.
- `wallTimeMs` (milliseconds): authoritative source = host-measured elapsed time (monotonic clock). Enforced via wall-clock deadline/epoch interruption.
- `peakLinearMemoryBytes` (bytes): authoritative source = the sandbox runtime's memory observer. Enforced via linear memory max limit.
- `hostcallBytes` (bytes): authoritative source = host-side accounting of data transferred across the sandbox boundary (imports/exports). Used for I/O cost attribution.

**Failure semantics per quantity:**
- `executionBudget` exhaustion → deterministic trap (catchable by host).
- `cpuTimeNs` exceeds ceiling → host terminates the sandbox (if CPU-time enforcement is available).
- `wallTimeMs` exceeds deadline → epoch interruption / external supervisor kill.
- `peakLinearMemoryBytes` exceeds limit → memory-allocation failure trap.

**Mapping to V4 `ExtensionProvenancePayload.resourceUsage`:** the V4 fields (`cpuMs`, `memoryBytes`, `timeMs`) are reinterpreted in V5 as follows:
- `cpuMs` → populated from `cpuTimeNs` if available; otherwise populated from `executionBudget` via a calibrated multiplier with a `measurementSource: 'fuel' | 'cpuTime'` discriminator field added.
- `memoryBytes` → populated from `peakLinearMemoryBytes`.
- `timeMs` → populated from `wallTimeMs`.
- New V5 fields: `executionBudget`, `hostcallBytes`, `measurementSource` (additive — does not break V4 readers).

`ExtensionProvenancePayload.capabilitiesExercised` is upgraded from a ceiling echo to an **authoritative set of WASI component imports actually invoked** (e.g. `wasi:filesystem.read`, `wasi:sockets.connect`). The host logs each capability invocation.

This is a **contract change** to `ExtensionProvenancePayload` (DOM-022): the `resourceUsage` and `capabilitiesExercised` fields change semantics from "ceiling" to "measured". This requires a successor architecture version (IAAS-DOM-ARCH-5) — V4 cannot be modified in place.

### Tenant Isolation and Compromise Containment (W019-AC06)

- **Tenant isolation:** structural. Each extension execution instantiates a fresh WASM module with no access to other tenants' data. There is no shared address space. Cross-tenant access requires the host to explicitly pass a shared-memory handle, which the runtime never does.
- **Compromise containment:** a compromised WASM module is trapped inside the sandbox. It cannot access the host filesystem, network, or memory except through granted WASI handles. Escape requires a vulnerability in the WASM runtime (Wasmtime/Wasmer), which is a separately tracked security concern.

### Portability/Deployment/Operational Trade-offs (W019-AC07)

- **Portability:** WASM bytecode runs anywhere a WASI runtime is available. Vercel (Node.js + Wasmtime native addon), self-hosted (any WASM runtime), edge (native WASM support).
- **Deployment:** the platform bundles a WASM runtime (Wasmtime via `@bytecodealliance/wasmtime` or similar). Extensions are distributed as `.wasm` files (future Marketplace/SDK concern, not this ACR).
- **Operational complexity:** low. Single runtime dependency, no container daemon, no image registry.

### Fallback/Unavailability Semantics (W019-AC08)

When the preferred sandbox (WASM/WASI) is unavailable:

1. **Runtime detection:** at bootstrap, `initializeBootstrap()` probes for the WASM runtime. If unavailable, it logs a warning and installs a `NoOpExtensionProvenanceSink`-style fallback: a `DegradedSandboxPolicy` that **denies all extension execution** with `denialReason: 'sandbox_unavailable'`.
2. **Denial behavior:** `ExtensionRuntime.executeExtension` checks the sandbox policy before dispatch. If `DegradedSandboxPolicy`, it emits failed provenance with `denialReason: 'sandbox_unavailable'` and throws `ValidationError`.
3. **Container fallback (future):** a future Work Item MAY implement a `ContainerSandbox` as a fallback for environments where WASM is unavailable but containers are. This is NOT authorized by this ACR — it requires a separate ACR and architecture version.
4. **No silent degradation:** the platform never executes an untrusted extension without a sandbox. If no sandbox is available, execution is denied.

### Decision Impact on V4 (W019-AC09)

- **V4 remains FROZEN.** This ACR does NOT modify V4 in place.
- **IAAS-DOM-ARCH-5 is a CANDIDATE.** If the Architect approves this ACR, a successor architecture version `IAAS-DOM-ARCH-5` would be frozen by a separate freeze Work Item (analogous to WORK-015 for V4). V5 would:
  - Inherit all V4 contracts unchanged.
  - Promote `DOM-P05` (Sandbox Technology) from OPEN/RESEARCH to FROZEN-CONTRACT.
  - Freeze the WASM/WASI trust boundary, capability enforcement, resource metering, and fallback semantics defined in this ACR.
  - Update `ExtensionProvenancePayload.resourceUsage` and `capabilitiesExercised` semantics from "ceiling" to "authoritative measured".
- **No implementation is authorized by this ACR alone.** Sandbox implementation requires a separately approved architecture version (V5) and bounded implementation Work Items.

## Architectural Questions Resolved

1. **What is the sandbox trust boundary?** The WASM component/instance boundary. Code inside the component is untrusted; the ExtensionRuntime host is trusted.
2. **Which layer is authoritative for capabilities and resource ceilings?** `ExtensionRuntime` (unchanged from V4 §2.6). The sandbox enforces the ceiling at the operation boundary.
3. **How are sandbox credentials/capabilities granted and revoked?** Granted at instantiation via imported WASI component handles; revoked via the architectural termination contract (terminate sandbox execution context — concrete API is an implementation choice, e.g. dropping the Store in Wasmtime).
4. **What happens to an in-flight execution on revocation or sandbox termination?** The host invokes the architectural termination contract (terminate sandbox execution context → failed provenance → re-throw). The concrete mechanism (e.g. Store drop in Wasmtime) is an implementation choice. Failed provenance is emitted with `denialReason: 'revoked_mid_execution'`. The error is re-thrown.
5. **Which resource measurements are authoritative for provenance?** Five distinct quantities (per AR-019-02): `executionBudget`/`fuelUnits` (deterministic execution budget, NOT CPU time), `cpuTimeNs` (host-measured CPU time, if available), `wallTimeMs` (host-measured elapsed time), `peakLinearMemoryBytes` (runtime-observed memory peak), `hostcallBytes` (host/guest transfer accounting). Fuel is NOT equated to CPU milliseconds. See §Provenance and Authoritative Resource Measurement for the full model.
6. **What minimum isolation guarantee is required across tenants?** Structural: no shared address space, no shared filesystem, no shared network. Each execution is a fresh instance.
7. **What is the fallback behavior when the preferred sandbox is unavailable?** Deny all untrusted extension execution with `denialReason: 'sandbox_unavailable'`. No silent degradation.
8. **Does the decision require a new architecture version?** Yes. The provenance `resourceUsage`/`capabilitiesExercised` semantics change from "ceiling" to "measured", which is a contract change requiring IAAS-DOM-ARCH-5.

## Alternatives Considered

### Container isolation as the preferred sandbox
Rejected as primary: portability (Vercel/edge do not support arbitrary containers), operational complexity (image registry, daemon), and coarser metering. Retained as a documented future fallback for native-system-access extensions.

### Native/plugin-process isolation
Rejected: poor portability, poor compromise containment (in-process), weak capability enforcement. Not suitable for untrusted extensions.

### Keep sandbox OPEN/RESEARCH (no decision)
Rejected: blocks Marketplace (DOM-P05) and SDK (DOM-P06) promotion, leaves compromise containment unsatisfiable, and leaves provenance `resourceUsage` as a ceiling echo rather than an authoritative measurement.

### Hybrid (WASM primary + container fallback in the same architecture version)
Rejected for this ACR: the container fallback requires additional evaluation (image distribution, capability profiles, cgroup metering) that is not mature enough to freeze. A separate future ACR may propose it.

## Compatibility / Migration Impact

- **V4 contracts unchanged.** ExtensionRegistry, ExtensionRuntime, ExtensionProvenance (implemented in WORK-016/017/018) remain as-is. The sandbox is a new layer that the runtime invokes; it does not change the existing service signatures.
- **ExtensionProvenancePayload semantics change in V5.** `resourceUsage` and `capabilitiesExercised` change from "ceiling" to "measured". Existing V4 provenance records (ceiling echoes) remain valid historical records; new V5 records carry measured values. A version field in the payload may be added to distinguish.
- **No data migration.** Existing PostgreSQL `ExtensionProvenance` rows are unchanged. The V5 semantics apply to new emissions only.
- **No breaking API changes.** `executeExtension`, `reverseExtension`, `verifyExtension` signatures are unchanged. The sandbox is internal to the runtime.

## Verification Impact

- **Static tests:** prove V4 remains FROZEN (no in-place modification); prove no sandbox implementation is introduced (no WASM/container/native runtime imports in `src/lib/services/`); prove ACR-004 exists with the required fields.
- **Architecture contract tests:** prove the Extension Stack anti-dependencies (V4 §2.9) are unchanged.
- **Regression tests:** prove `ExtensionProvenancePayload` structure is unchanged (fields are the same; semantics change is documented in the ACR, not enforced by tests until V5 implementation).
- **No runtime tests.** This ACR authorizes no implementation. Implementation tests are deferred to future Work Items under V5.
